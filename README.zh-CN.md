## 1. 先读这一段：这不是广播 CAN 帧

**这辆车的 OBD-II 口后面有网关，收不到任何周期广播帧。** 第一轮上车被动监听 24.8 分钟、59 万帧，16 个 CAN ID 全是 `18DAxxxx` 诊断帧；钥匙 ON、怠速、行驶全程广播帧数为 0。所以本文档里的每一个数字都是**主动问、ECU 答**得来的：UDS 服务 `22` ReadDataByIdentifier 的正应答字节。

因此这份参考的主键是「**模块地址 + DID + 字节 / 位位置**」，不是 CAN ID。同一条物理通道上靠 29 位 ID 里的目标地址区分 4 个（已解码）ECU。

**DBC 不适合作为主格式**：DBC 描述的是周期广播帧的布局，而这里没有广播帧可描述。要机器读，请用本目录的 `signals.json` / `signals.csv`，或 OBDb 兼容的 `obdb-signalset.json`。

## 3. 快速上手

读一个 DID、解一个信号。下面的例子用 [python-can](https://python-can.readthedocs.io) 加任意一个 ISO-TP 库读机油温度（ECM `0x10`，DID `0x268F`，数据区第 15 字节，`raw − 40 °C`）。**全程只发服务 `22`。**

```python
# pip install can-isotp python-can
import isotp, can

bus = can.interface.Bus(channel="can0", interface="socketcan", bitrate=500000)
addr = isotp.Address(isotp.AddressingMode.Normal_29bits,
                     txid=0x18DA10F1, rxid=0x18DAF110)   # 请求发给 ECM, 应答从 ECM 回来
stack = isotp.CanStack(bus, address=addr, params={"tx_padding": 0x55, "blocksize": 0, "stmin": 0})

stack.send(bytes([0x22, 0x26, 0x8F]))                   # ReadDataByIdentifier 0x268F
payload = stack.recv(block=True, timeout=1.0)           # 62 26 8F <54 字节数据>
data = payload[3:]                                      # 去掉 62 + DID 回显: 偏移 0 就是 data[0]
print("机油温度:", data[15] - 40, "degC")
```

三件事不做就会碰壁：

- **流控帧必须立刻回。** 应答 54–63 字节，走首帧 + 8–9 个连续帧；诊断仪要在几毫秒内发出 `30 00 00`，晚了这台 ECU 直接放弃整笔传输。
- **请求补足 8 字节**（本车的诊断仪请求用 `0x55` 填充，流控用 `0xAA`）。
- **本文档的偏移从 `62 + DID` 回显之后算起**，`[a:b]` 不含 b，`value = raw × scale + add`。

采集这份数据的车不需要会话控制、也不需要安全访问。那是**那辆车**的性质（ECU 已解锁），不一定适用于你的车；如果读取被拒绝，不要去找绕过的办法——见安全声明一节。

## 4. 怎么读取：寻址、服务、时序与预算

| 层 | 事实 |
|---|---|
| 物理 | OBD-II 口：6 脚 CAN-H、14 脚 CAN-L、4 脚 GND、16 脚 12 V 常电。**6 / 14 按插进车的公头方向数**（数反会得到 0 帧） |
| 链路 | 经典 CAN 2.0B，500 kbit/s，单帧 ≤8 字节，**无 CAN FD**（12 份日志约 190 万帧，FD 帧计数 0）。只证明网关外的 OBD 侧 |
| 寻址 | 29 位 ISO 15765 物理寻址：请求 `18DA<目标>F1`，应答 `18DAF1<目标>`；诊断仪地址固定 `F1`。点名全车用功能广播 `18DB33F1`。11 位 `7E0/7E8` 上 Mode 01 无任何应答 |
| 传输 | ISO 15765-2：请求单帧 `03 22 <DID 高> <DID 低>`，用 `0x55` 填满 8 字节；应答 54–63 字节数据区 = 首帧 FF + 8–9 个连续帧 CF。**流控 `30 00 00`（填充 `0xAA`）必须在几毫秒内回，晚了 ECU 直接放弃** |
| 应用 | UDS 服务 `22` ReadDataByIdentifier。本车默认会话免握手（不需要 `10 03`，更不需要 `27`）；`3E` 保活实测不需要（600 s 连续采样零错误）。**这条只在本车验证过** |
| 偏移口径 | 本文档的 offset 指**去掉应答头 `62 + DID 两字节` 之后的数据偏移**，`[a:b]` 不含 b；`value = raw × scale + add`。默认大端，明确标注小端的除外 |

### 4.1 每事务耗时（主机侧观测值，不是 ECU 硬限制）

| 模块 / DID | 请求→完整 p50 | p95 | 相邻连续帧间隔 |
|---|---:|---:|---|
| ECM `10:2610` | 24.9 / 27.4 ms | 30.7 / 30.6 ms | ≈2 ms |
| ECM `10:2611` | 29.3 ms | 33.5 ms | ≈2 ms |
| ECM `10:268F` | 27.3 ms | 29.8 ms | ≈2 ms |
| VSA `28:4001/4004/4007/4073` | ≈100.1 ms | ≈100.6 ms | ≈10 ms |
| EPS `30:48BD/48C0/48C4` | ≈67.9 ms | ≈69 ms | ≈8 ms |

**这些是主机侧观测值，不是 ECU 的硬限制。** 「VSA 80 ms」是首帧到末帧的整段，不是帧间隔，也不能断定是 STmin 硬限制（采集用的适配器无硬件时间戳）。

**串行模型成立**：2051 轮逐轮恒等式 `周期 = Σ(请求→完整) + Σ(间隙)` 残差为 0，轮间开销 1.48 ms/轮。由此得到**单 ECU 串行上限 ≈ 1 s / 30.5 ms ≈ 33 Hz（仅 ECM）**。跨模块并发协议上允许（不同地址各挂一个未完成请求），**本车从未验证**；按模块求和再取最大的理想周期只比串行快约 28%，不是 100 ms。

作为对照：FlashPro 自己轮询 `22 2610` 与 `22 2611` 各 **18.13 Hz**。

两条采集纪律（吃过亏才写下的）：① 一笔请求超时会触发对该地址的隔离，采样组的第一笔要放最稳的 DID；② **行驶中不要把扫描和核心采样混在一条串行链上**——边行驶边扫描的一份日志里核心采样最长断流 7.891 s，纯核心采样的另一份最长只有 1.244 s。

## 6. 数据字典：文件与字段

`data/signals.csv` 与 `data/signals.json` 的 `signals[]` 每行一个信号，字段如下：

| 字段 | 含义 |

|---|---|

| `module_address` | 诊断目标地址，如 `0x10`。请求 ID `18DA<地址>F1`，应答 `18DAF1<地址>`。 |
| `module` | 该 ECU 的名称。 |
| `did` | 服务 `22` 读的数据标识符。 |
| `response_length` | 数据区字节数，即正应答去掉 `62 + DID` 回显之后的长度。 |
| `name` / `name_en` / `name_zh` | 信号的稳定标识符、英文显示名与中文名。 |
| `offset` | 数据区里的字节偏移（偏移 0 = `62 + DID` 回显之后的第一个字节）。 |
| `size_bytes` | 应用掩码之前的字段字节宽度。 |
| `bit_mask` | 只有位字段才有；掩码作用在按 `endian` 拼出的 `size_bytes` 整数上，**不右移**。 |
| `bit_length` | 位宽（没有掩码时等于 `size_bytes × 8`）。 |
| `endian` | 多字节字段的端序。 |
| `signed` | 原始整数是否为补码有符号。 |
| `scale` / `add` | `value = raw × scale + add`。 |
| `unit` | 解码值的单位。`unresolved`、`?`、`raw` 表示物理单位确实未确定。 |
| `value_min` / `value_max` | 原始值满量程映射出的理论范围。**不是**实测范围，**不是**工作限值。 |
| `observed_samples` / `observed_min` / `observed_max` | 全部采集里实际出现过的样本数与极值；没采过就是空。位字段这里给的是**掩码后的原始值**，不是 0/1。 |
| `confidence` | `high` / `medium` / `low`，与解码表逐字一致。 |
| `evidence` | 一句话说明置信度依据什么。 |
| `source_report` | 哪一次采集或分析最先确立它。 |
| `enum` | 已知的取值 → 含义。 |

置信度只表示「在这一辆车上证据有多强」：

- **`high`**——与独立显示逐点对上，或与调校工具未取整导出逐列拟合到 r≈1，或有干净前后对照的明确动作。仍然**不代表**已独立标定，**不代表**在原厂车上成立。
- **`medium`**——一致且可复现，但依赖单次观察、假设的刻度、推定的顺序，或未在本车完全验证的公开来源。
- **`low`**——候选。位置与数据形态是真的，物理身份或刻度没有确立。不要拿它做任何东西。

- `data/signals.json`——完整导出（含本文档全部结构化内容：模块、信号、候选、不可辨识、已推翻、局限、安全声明、数据版本）。
- `data/signals.csv`——信号总表的表格形式，字段与第 5 节一致。
- `signalsets/v3/default.json`——[OBDb](https://github.com/OBDb) `signalsets/v3` 兼容的 signalset。**只收录置信度为「已确认（研究级）」与「中」的信号**；低置信与候选留在本文档里，不进 signalset。位坐标按 OBDb 的 MSB0 约定换算（`byte = bix // 8`，`bit = 7 − (bix % 8)`），比例以 `mul` / `div` 表达，单位取 OBDb 的枚举值、无对应枚举时记 `unknown` 并在 `description` 里写明原单位。

三份产物由同一批来源产出；`tools/validate.py` 会校验它们互相一致，CI 每次提交都跑。

`已确认（研究级）`的含义是「本车上证据强」——与独立仪表逐点对上、或与调校工具的未取整导出逐列拟合到 r≈1、或有明确的动作对照。它**不代表**已用独立仪器标定，也不代表在原厂车上成立。

「实测范围」是全部采集样本里出现过的最小 / 最大值与样本数（不含均值），只说明**观察到过什么**，不定义量程、不定义报警阈值。空白表示该信号在统计里没有样本。

## 11. 被动收到的广播帧

**基本上没有。** 这辆车的 OBD-II 口后面有网关，钥匙 ON、怠速、行驶全程都收不到周期广播的车辆 CAN 帧——这是本文档全部内容都来自主动轮询的原因。

归档里唯一一条不属于「我们问、ECU 答」的重复出现的帧，是被动监听 Hondata FlashPro 那一轮记录到的 **11 位 ID `0x784`，数据 `01 00 7E 6A 00 00 00 00`，约每 2.51 s 一次**。它的发送方与含义都未确认（那一轮总线上同时挂着 FlashPro，不能排除是诊断工具自己发的）。本文档不据此给出任何解码。

另外在诊断侧见过两个非常规地址：功能广播 `18DBEFF1` 出现过一次，`18DAF1EF` 出现过两次。它们仍属诊断问答，不是车辆广播。

如果你要的是底盘广播量（`opendbc` 里那类），需要接到网关内侧的 F-CAN 上——候选接线点是前摄像头 12 针插头或仪表 A 连接器 32 针。本项目**没有接过**，所以不提供任何 F-CAN 的结论。

## 12. 方法与证据纪律

**相关不等于识别。** 只有逐样本精确比对（原始值相等 / 固定位移 / 固定常差）才写进解码表。怠速 10 分钟里所有慢变量互相都相关，这类相关一律不算证据。

**峰值与计数一律从完整日志算**，不在日志还在写入时出统计——曾因此把 15,976 包写成 11,779 包、把 +1.16 bar 写成 +0.85 bar。

**口头标记（MARK）比总线上的事件晚 16–40 秒**，反复出现过。所以时间对照一律用总线里的事件（刹车压力、转速归零）作锚，口头标记只作补充索引；找快变量用「保持状态 30 秒」的办法。

**找枚举位只在原地做**（行驶量会淹没它），**找动态量只在行驶时做**；并且要用无切换的对照日志反查候选位是不是行驶量。

**否定结论要限定条件**：只能说「在当前采样率 / 编码 / 这批 DID 里未识别」，不能说「不存在」。这条是被推翻次数最多的一类结论（纵向 G、离合都曾被错误地否定过）。

**分级证据 + 停止条件**：每条假设先写清什么算 supported、什么算 refuted、什么叫样本不足，再去数据里查；样本不足就记 `insufficient`，不四舍五入成结论。本文档里的「不可辨识」一节就是这么来的。

**四层证据分开报**：格式通过 ≠ 主机接受 ≠ 屏幕显示正确 ≠ 原厂车可用；数值对上 ≠ 已标定。

## 13. 已知局限与还缺什么数据

- **只有一辆车**：全部结论来自同一辆装了 Hondata FlashPro 的 FL5。原厂车的默认会话是否同样免握手、`268F` 是否同样应答，**都没验过**。
- **没有独立仪器**：油压的参考面（表压 / 绝压）、偏航与横向 G 的刻度、转向角的 °/LSB、废气阀的单位，全部缺独立标定。文档里给的比例是研究拟合值，不是标定值。
- **采样率低**：研究期的轮询速率远低于 FlashPro 的 18 Hz（多数扩展量 0.2–1.2 Hz）。亚秒瞬态、快计数器在这个采样率下必然混叠——ADS `520A` 的计数器检验就因此只能记「样本不足」。
- **扫描覆盖不全**：VSA `A083–FFFF`、EPS `2A31–FFFF`、仪表 `7000–70FF` 以外的全部、网关 `ED`/`EF`、`0x70`、Honda Sensing 子单元都没扫过。
- **负温与极端工况没有数据**：外温的负温编码在采集地永远验不了；连续的冷启动到热平衡记录也还缺一份。
- **还缺什么数据（不需要专门去开车，日常通勤连续采集自然会覆盖）**：① `2610[39]` 的 state 2 需要 ≥10 次独立高增压事件且采样间隔 ≤0.1 s；② 需要一段气压明显不同的旅程才能分开绝压与表压；③ `268F` 闩锁需要 ≥10 次置位事件；④ `2611` 尾部需要一个绝对值 >127 的样本才能定位宽；⑤ Brake Hold 需要 ≥20 次带同速率踏板证据的停车事件；⑥ 「恒定 DID」需要在若干个自然点火周期里各读一次。
- **需要外部参考才能收敛的**：偏航率的外部参考（≥10 Hz、误差 <3%）、实测轮距与滚动周长、横向 G 的独立标定、`3004` 的独立真值（维护记录 / 仪表读数 / 厂商文档）。服务 `24`（读定标）已两次返回 `0x11`，这条路走不通。
